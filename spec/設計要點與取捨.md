本文件收錄本專案跨流程 / 較小但有取捨的設計決策，供後續開發與測試遵循。流程級的完整描述見 `spec/流程_*.md`；本文件只記「為什麼這樣決定、取捨了什麼」。有疑慮先查本文件，未提到則提出討論再修編（見 `CLAUDE.md`「測試有疑慮或取捨」）。

## ADR-001: `token='sys'` 開發模式登入捷徑

- **背景**：開發 / e2e 需免帳密直接以管理員身分進入頁面。
- **決策**：URL 帶 `?token=sys` 時，**demo 入口 `srv.mjs` 之 `getUserByToken`** 對該 token 直接回傳系統管理員 user，前端 `w-ui-loginout` 於 localhost 自動帶入。
- **層級界定**：此捷徑位於 **`srv.mjs`（套件之 demo/範例入口）**，**非套件本體 `WWebApi.mjs`**。套件使用者部署時自行提供 `getUserByToken`，不受此 demo 捷徑影響。
- **取捨**：已加 `process.env.NODE_ENV !== 'production'` 守門（dev/e2e 可用、production 自動停用，避免 demo 若被當正式入口時 `'sys'` 成為後門）。正式部署須由使用者提供真實 `getUserByToken`（解析真實 token）並以真實機制取代範例 `verifyClientUser`/`verifyAppUser`。
- **落地**：`srv.mjs`（demo getUserByToken 之 `'sys'` 分支 + NODE_ENV 守門）、`src/App.vue`；詳 `spec/流程_展示API文件.md`「契約」。

## ADR-002: 資料由後端 syncData 推送驅動，前端不輪詢

- **背景**：左側 API 樹與右側文件需隨 DB 變動即時反映。
- **決策**：後端將 `apis` 資料表透過長連線推送前端，寫入 `store.state.apis`；`LayoutContent` 監看其變動重建樹。前端不主動輪詢。
- **取捨**：存 / 刪後不由前端手動改樹，一律等後端推送重建——換取單一資料源與一致性，代價是「更新時機綁定推送鏈」。
- **落地**：`src/main.js`、`src/store/mutations.mjs`、`src/components/LayoutContent.vue`、`server/procApis.mjs`。

## ADR-003: API 編輯以「id 是否存在」分流 update / insert

- **背景**：同一張編輯表單同時承載「改既有 API」與「新增 API」。
- **決策**：表單帶原 `id` → 後端 `funNew` 保留原 id 走 update（原地更新、舊名消失）；新增表單 `blankApi` 無 id → `funNew` 產生新 id 走 insert。
- **取捨**：以「id 有無」單一條件分流，不另設 mode 旗標——簡潔，代價是「blankApi 不可帶 id」成為 load-bearing 約束。
- **落地**：`server/procApis.mjs`、`src/schema/tables/apis.mjs`、`src/components/LayoutContentEdit.vue`；詳 `spec/流程_編輯API.md`。

## ADR-004: UI 非同步提交統一 `core()` 五段；可預期錯誤走 inline 紅字

- **背景**：提交按鈕需一致處理 loading、同步檢測、API 失敗、非預期例外。
- **決策**：所有「呼叫後端的 UI 函式」走 `core()` 五段（清空舊錯 → 同步檢測 early-return → 開 loading → 各 async 各自 catch + 旗標短路 → finally 關 loading）。可預期錯誤設 inline 紅字不打斷表單，非預期例外才 `$alert` 兜底。
- **取捨**：固定結構換取可預期性與可測性；inline 紅字 vs alert 的分流由「錯誤是否可預期」決定。
- **落地**：`src/components/LayoutContentEdit.vue`；詳全域 `CLAUDE.md §5.1` canonical 範本與 `spec/流程_編輯API.md`「錯誤處理分層」。

## ADR-005: 成功訊息用 `showCheckYes` modal 取代 toast

- **背景**：存 / 刪成功需給使用者確認，且 e2e 須能穩定截圖該終態。
- **決策**：成功訊息由 toast 改為 `showCheckYes` 模態（停留、需點 OK），與刪除確認 `WConfirm` 同款。
- **取捨**：toast 是「插入後又移除」的暫態 DOM，新版 chromium 在 insert/remove 後會整頁偏移 1px 造成 e2e baseline 不穩；modal「顯示著被截」無移除殘留、byte 穩定。以多一次點擊換取截圖穩定與 UX 一致。
- **落地**：`src/components/LayoutContentEdit.vue`；詳 `spec/流程_編輯API.md`「契約」。

## ADR-006: API 測試一律經後端 proxy 繞過 CORS

- **背景**：「測試」分頁要對任意目標 API 送請求，瀏覽器直打會撞 CORS。
- **決策**：前端不直接打目標，一律呼叫後端 `proxyRequest` 由後端代送（原 axios；ADR-029 起改 Node 內建 fetch），timeout 硬編碼 30s。
- **取捨**：多一跳後端換取繞過 CORS 與統一控管；目標須通過後端 `isAllowTarget` 白名單，非 http(s) 或不允許者 reject。
- **補記（`isAllowTarget` 白名單鉤子預設未接線）**：`procProxy` 雖內建 `isAllowTarget` 鉤子（`procProxy.mjs:17`、`:44-50` 為 function 才檢查、回 `false` 才 reject `errReqTargetNotAllowed`），但 `WWebApi.mjs:290` 實際以 `procProxy({ srLog })` 建立，**只傳 `{ srLog }`、未傳 `isAllowTarget`** → 鉤子為 `null`、檢查整段跳過，目前對任意 http(s) 目標皆代送。此為當前部署形態（管理員自用、本機 / 受控環境）下的取捨。**啟用條件**：若部署於可觸及內網或雲端 metadata 端點（如 `169.254.169.254`）之環境，須於 `WWebApi.mjs` 建立 `procProxy` 時傳入 `isAllowTarget`，拒 loopback（`127.0.0.0/8`、`localhost`）、私網（`10/8`、`172.16/12`、`192.168/16`）與 link-local（`169.254/16`）以防 SSRF。
- **落地**：`server/procProxy.mjs`、`src/components/LayoutContentTest.vue`；詳 `spec/流程_測試API.md`「契約」。

## ADR-007: proxy 對 4xx/5xx 視為「有回應」

- **背景**：被測 API 回 4xx/5xx 是正常測試結果，不該被當成 proxy 失敗。
- **決策**：4xx/5xx 也走成功 resolve（原 axios 以 `validateStatus: () => true` 達成；ADR-029 起改 fetch，其對 4xx/5xx 本就不 throw），由回應面板顯示其狀態碼與 body；僅 timeout/DNS/連線拒絕等 fetch 例外才 reject。
- **取捨**：把「HTTP 狀態碼」與「proxy 是否成功」解耦——使用者能看到真實狀態碼，代價是呼叫端須自行判讀狀態碼語意。
- **落地**：`server/procProxy.mjs`；詳 `spec/流程_測試API.md`「回應狀態分流」。

## ADR-008: Email 模板標題 / body 分離存放

- **背景**：寄信功能的標題與內文需可維護、可 i18n。
- **決策**：標題走 `server/procLang.mjs` 語系鍵（eng + cht）；body HTML 放 `server/template/<purpose>Email-{eng,cht}.html`，`{placeholder}` 由 `procCore.renderEmailBody` 發信時代入。

## ADR-009: pixel baseline 採 pixelmatch 容差比對（非 byte-exact）

- **背景**：早期 baseline 用 `buf.equals` 逐位元組精確比對，受 SVG icon / 字型跨 session 反鋸齒光柵化的次像素差影響而偶發 flake，須反覆手動調研。
- **決策**：改用 `pixelmatch`（`includeAA:false` 反鋸齒感知）+ `maxDiffPixels` 容差（預設 100、threshold 0.1）；失敗時將 capture / baseline / **diff 標紅圖** 雙存 `testPending/`（ms timestamp + 撞檔 -N 永不覆蓋）。對齊 `w-web-sso` 之 `assertBaselineMatch`。
- **取捨**：反鋸齒殘留（個位~數十 px）被忽略不再 flake；真 regression（icon 換 / 版面位移 / 顏色 / 內容變）動輒數百~數千 px 仍被抓到。容差只放輔助層，**主驗證仍以語意斷言為準**（全域 §6.2）。需更嚴/更鬆可由呼叫端覆寫 `opts.maxDiffPixels`/`threshold`。
- **落地**：`test/tools/e2e-setup.mjs` `assertOrRegenBaseline`。

## ADR-010: e2e 截圖穩定以 WDrawer `[state]` 屬性判定 + captureStable 多重 settle

- **背景**：抽屜（WDrawer）開 / 合是平移動畫，截圖若停在過渡態會 byte 不穩；舊作法量搜尋框幾何 `x>=0` 在收合態永遠 false → 空轉到 10s timeout，且高負載下會誤判中間態。
- **決策**：`waitDrawerReady` 直接讀 WDrawer 根節點 `[state]`（`hidden`/`opening`/`opened`/`hiding`），等全部進入穩定態（`opened` 或 `hidden`）才放行——事件驅動（transitionend），不受 CPU 負載影響。`captureStable` 再疊 park mouse、initialWait、拖曳分隔條 opacity 輪詢、SVG SMIL 凍結、`fonts.ready`、retry-until-stable。
- **取捨**：以「讀元件狀態機」取代「量幾何輪詢」——收合 / 展開雙向皆準、一穩定即放行（抽屜 case 從 ~22s 降到 ~13s）。沿用 `w-web-sso` 作法。
- **落地**：`test/tools/e2e-setup.mjs` `waitDrawerReady` / `captureStable`。

## ADR-011: 回應卡非決定性欄位以遮罩處理；右對齊浮動值用固定寬度錨右緣遮罩

- **背景**：測試流程回應卡含 `durationMs`、headers `date`/`etag` 等每次不同的非決定性欄位，會使 baseline 永遠不一致。
- **決策**：截圖時以黑色遮罩遮去非決定性區域再做 baseline；狀態碼、body 為決定性，保留比對。`durationMs`（`.w-tnum`）右對齊、位數變動會使元素左緣浮動 → 遮罩改為**錨定右緣 + 固定寬度**（W=100px 涵蓋最大位數），避免遮罩邊界隨位數浮動造成邊緣 byte flake。
- **取捨**：犧牲非決定性區域的視覺比對，換取 baseline 可穩定；遮罩寬度取固定值而非依元素尺寸，是因為元素本身寬度即為 flake 來源。
- **落地**：`test/tools/e2e-setup.mjs` `captureStableWithBox`（`opts.mask` 支援 `{ sel, fixedWidth }`）、`test/e2e-apitest.test.mjs`；詳 `spec/流程_測試API.md`「非決定性欄位」。

## ADR-012: e2e hermetic seed（每 case 重置 base seed）

- **背景**：多個 e2e / 多 case 共用同一 DB，殘留資料會污染後續測試與 baseline。
- **決策**：`resetToBaseSeed` 清空 `apis` 表再插入固定 base seed（`ds.apis.funTest()`，固定 id）；每個 case `beforeEach` 重置、`afterEach` 再清，確保從相同已知狀態起跑。
- **取捨**：每 case 重置有成本，換取 hermetic（單跑與全跑一致、case 間不互相污染）。
- **落地**：`test/tools/e2e-setup.mjs` `resetToBaseSeed`；各 `test/e2e-*.test.mjs` 的 `beforeEach`/`afterEach`。

## ADR-013: e2e 雙語覆蓋（eng + cht 各一輪）

- **背景**：UI 全面 i18n，單語測試會漏掉語系切換 / 翻譯缺漏的 regression。

## ADR-014: 按鈕雙擊防護（實作為頁面層全頁 overlay）

- **背景**：有副作用的提交按鈕（存 / 刪 API）若被連點或 API 被直打，會重複執行。
- **決策**：本專案實際採**頁面層**防護——存 / 刪確定打 API 才 `updateLoading(true)` 開全頁 overlay（`LayoutContentEdit.vue` `submitSave`、`doDelete`），overlay 期間擋住使用者再次互動，避免 async API 進行中的二次點擊。本專案**未**引入元件層 `:promiseUnlock` 與後端層 mutex：存 / 刪按鈕為原生 `<button @click>`（非 `WButtonCircle`/`WButtonChip`），後端 `server/` 下亦無 `procMutex.mjs`。
- **取捨**：本工具為管理員自用（連線已由 `verifyClientUser` 限管理員，非開放公眾），併發攻擊面小；且後端 `saveApi` 依 `id` upsert（`procApis.mjs:16-38`，有 id 走 update、無 id 走 insert）、`deleteApi` 依 `id` del（`procApis.mjs:41-51`）皆為冪等操作，同一筆重入只是覆蓋成同一結果或刪同一筆，後果有限。故以頁面層 overlay 為足夠防護，不另加元件鎖與後端 mutex（避免為單人自用工具引入不必要複雜度）。
- **落地**：`src/components/LayoutContentEdit.vue`（`submitSave`/`doDelete` 之 `updateLoading(true)`）、`server/procApis.mjs`（依 id upsert/del 冪等）。

## ADR-015: 訊息 i18n — 一律走 procLang msg-key、依 lang 反查（成功與錯誤；參考 w-web-sso ADR-034）

- **總則（msg-key）**：所有給使用者看的文字訊息（**成功與錯誤皆然**）一律是 **procLang 的 msg-key**，由前端依當前 lang 反查顯示，不寫死任何語言文字。成功 key（如 `saveSuccess`、`deleteSuccess`）與錯誤 key（如 `errReqUrlInvalid`）性質相同、同住 procLang、同樣 lang 反查；差別只在「執行當下這個 key 由誰提供」——成功由前端給（前端知道操作成功 → `$t('saveSuccess')`）、錯誤由後端 reject 給（前端 `$transErr` 反查）。`err` 前綴僅標示「此 msg-key 屬錯誤類」，非另一套機制。
- **回傳契約（單一回應「非 key 即 data」，不混用 `{key,msg}` 信封）**：
  - **成功**：若回的是「文字訊息」（有語系問題）→ 回 **key**，前端依 lang 查文字；若回的是「指定數據」（如清單）→ 直接回 **數據**（不回 key）。
  - **錯誤**：一律回 **key**，前端依 lang 查文字。
  - **對外部應用查詢數據**：成功回 **數據**、錯誤回 **key**；key 對應文字清單僅在外部有需要時才提供。
  - **不採 `{key,msg}` 信封**：經盤查（每個 fapi 不是「純訊息」就是「純數據」、無「訊息＋數據併回」場景），本專案無此需求，故一個回應只會是 key 或 data 其一，不包雙層信封。
- **背景**：後端原本 reject「原始英文人話字串」（`'invalid url'`、`'invalid id'`…），前端 `String(err)` 直接顯示 → 不論使用者語系都顯示英文、且生字串散落無法在地化。
- **決策**：後端錯誤一律走 **err-key（msg-key 之錯誤類）**——
  1. **後端 reject err-key**：proc 層（procProxy/procApis/WWebApi）發生可預期錯誤時 `reject('errXxx')`（key 名 = procLang 字典 key），不再回原始人話。每個 err-key **須於 `server/procLang.mjs` 建立 eng/cht 文字**。
  2. **後端 log err-key**：以 `server/srLog.mjs`（包 `w-syslog`，比照 SSO）於 kpFunExt 邊界 `srLog.error({ event, err })` 統一記錄 err-key 供識別；axios 等動態例外另 log 真實訊息、但回前端只給 key（如 `errProxyRequestFailed`）。
  3. **前端依 lang 反查顯示**：前端 catch 拿到 err-key 後以 `$transErr(err)`（`src/main.js`）依當前 lang 反查 procLang 顯示在地化文字；非字串或查無 key 則 fallback `anUnexpectedErrorOccurred`，不顯示生 key。
  4. **其他外送管道（如 email）**：若後端成功/失敗須回傳至前端以外管道（email 通知等），須由**前端呼叫時傳入 `lang`**，後端用該 lang 查 procLang 取在地化文字再產製（對齊 SSO `getEmailTitle/renderEmailBody(lang)`）。本專案目前無寄信功能，列為日後新增寄信之契約。
- **取捨**：與 SSO 現行做法一致——錯誤 reject **字串 key**（非 `{key,msg}` 物件；SSO ADR-034 早期的 `_tErr` 轉 `{key,msg}` 已被其自身推翻為 key-only 字串），本專案由**前端反查**（前端已有完整 `kpLang` 字典 + `$t`，免改 fapi 簽章傳 lang，更輕量）。曾評估改用 `{key,msg}` 雙層信封統一回傳，盤查後確認本專案無「訊息＋數據併回」場景而不採用（見上「回傳契約」）。email 類「其他管道」才比照 SSO 由前端傳 lang、後端解析。成功訊息之 msg-key 由前端提供並以 `$t` 反查（同為 procLang key，只是不經後端 reject；見 ADR-005）。constructor 啟動 throw（`invalid WOrm` 等，不達前端）維持原樣不 key 化（「除非必要」）。
- **落地**：`server/srLog.mjs`、`server/procProxy.mjs`、`server/procApis.mjs`、`server/WWebApi.mjs`（reject err-key + kpFunExt `wrapErrLog` 邊界）、`server/procLang.mjs`（err-key 字典）、`src/main.js`（`$transErr`）、`src/components/LayoutContentEdit.vue`/`LayoutContentTest.vue`（catch 改 `$transErr`）。

## ADR-016: `syncAndReplaceTabs` 為 delAll→insert 非原子（已知限制）

- **背景**：外部應用以 `/syncAndReplaceTabs` 整批同步某 group 之 `apis`（先清該 group 既有、再插入新一批）。
- **決策**：`WWebApi.mjs:571` 先 `woItems[keyTable].delAll({ group })` 刪除該 group 全部，再 `WWebApi.mjs:575` `procOrm(userId, keyTable, 'insert', rows)` 插入新批，**兩步非原子**（不包交易），中間若 insert 失敗會留下「已清空但未補回」的中間狀態。
- **取捨**：本工具為 admin 自用、底層 lmdb 為單寫程序（無多寫者並發），且 insert 失敗時外部可重新發起同步補回；引入交易對單人自用工具屬過度設計，故**不引入交易**，將「delAll→insert 非原子」記為已知限制。若日後改為多寫者並發或無法重試之場景，再評估交易或先插後刪之補償策略。
- **落地**：`server/WWebApi.mjs` `syncAndReplaceTabs`（`:571` delAll、`:575` insert）。

## ADR-017: `ssoAppToken` 為明文設定欄位（建議改 env 注入，待討論）

- **背景**：本專案登入 / 驗證委派 SSO，需以 app token 與 SSO 互動。
- **決策（現況）**：`ssoAppToken` 列為 `g_getSettings.mjs:16` 之**明文設定欄位**（預設空字串，部署時填入 SSO tokens 表中 `isApp=y` 之 app token）。同檔 `ssoBaseUrl`/`ssoLoginUrl` 一併為明文設定。
- **取捨 / 待討論**：明文設定便於本機開發與部署填寫，但機密直接落在原始碼檔有外洩風險（誤 commit、原始碼外流即洩漏）。**建議改由環境變數注入**（部署環境設 env，`getSettings` 讀 `process.env`，原始碼不留機密），此調整涉及部署流程與既有讀取點，**列為待討論**，未實作前維持明文設定欄位現況。

## ADR-018: `getUserByToken` 失敗一律回 `{}`，token 時效 / 撤銷完全委派 SSO

- **背景**：`WWebApi` 以注入之 `getUserByToken(token)` 解析使用者；本專案實作將 token 驗證委派 SSO。
- **決策**：`getUserByToken` 經 SSO 解析 token，**失敗一律回空物件 `{}`**（範例 `WWebApi.mjs:111`、生產環境提示 `:109-110` 加 SSO 驗證機制）；上層 `getTokenUser`→`checkUser` 對 `{}` 因缺 `id`/`email`/`name`/`isAdmin` 而 reject 對應 err-key，連線即被拒。本專案**不在本端維護 token 狀態**——token 是否仍有效、是否被撤銷、有效期長短，**完全委派 SSO**：每次請求都即時向 SSO 解析，SSO 認得即放行、不認得（含過期 / 撤銷）即回 `{}`。
- **取捨**：以「每次委派 SSO 即時解析」換取本端無 session 狀態（不需自管 token 過期 / 撤銷快取，單一真理在 SSO）；代價是每次驗證都依賴 SSO 可達與其判定，且本端無法獨立判別「token 無效」之細因（一律呈現為查無使用者）。此為刻意的設計邊界，非缺漏。
- **落地**：注入之 `getUserByToken`（範例見 `server/WWebApi.mjs:91-112`）、`getTokenUser`/`checkUser`（`server/WWebApi.mjs:342-361`/`:311-338`）。

## ADR-019: session token 經 URL `?token=` 傳遞之暴露面（已知取捨）

- **背景**：`/api/getUserByToken` 為未登入主頁時先檢測 token 之端點（w-ui-loginout 預設值）。
- **決策**：該端點為 `GET`、token 由 **URL query string** 帶入（`WWebApi.mjs:629` `get(req, 'query.token', '')`）；此為 w-ui-loginout 預設契約，兩端須同改故沿用。
- **取捨 / 暴露面**：URL 內的 token 會出現在伺服器 access log、瀏覽器歷史紀錄、以及（若頁面再外連）`Referer` 標頭，較易外洩。本專案沿用 w-ui-loginout 預設以保相容，將此暴露面記為已知取捨。**較佳作法**：後續對外主通道（WebSocket / API 連線）已改以 `Authorization: Bearer` **header** 帶 token（`WWebApi.mjs:858-862` `verifyConn` 由 `authorization` 取、刪 `Bearer ` 前綴），header 不落 access log / 歷史 / referer，安全性較佳；`?token=` 僅限主頁初次檢測之相容路徑。
- **落地**：`server/WWebApi.mjs`（`/api/getUserByToken` 之 `query.token`、`verifyConn` 之 `authorization` header）。

## ADR-020: 存 / 刪成功段未顯式 `updateLoading(false)`，靠 `.finally` 同 render flush 關閉

- **背景**：UI 規範要求 `showCheckYes` 之前先 `updateLoading(false)`，避免 loading overlay 疊在成功 modal 上影響告知效果。
- **決策（現況）**：`LayoutContentEdit.vue` `submitSave`（`:398`）與 `doDelete`（`:433`）之**成功段未顯式在 `showCheckYes` 前呼叫 `updateLoading(false)`**；關 loading 統一由各自外層 `core()` 之 `.finally`（`onClickSave` `:345`、`doDelete` `:439`）執行。
- **取捨**：`core()` return 後 `.finally` 與 `showCheckYes` 渲染落在同一輪 render flush，loading 之關閉與成功 modal 之出現對使用者而言不可見地同時發生，e2e baseline 實測無可見重疊（成功終態截圖未見 loading overlay 殘留）。故維持「`.finally` 統一關 loading」之單點寫法、不在成功段另插 `updateLoading(false)`（避免重複關閉與分散控制點）；此為已驗證無視覺重疊之取捨。
- **落地**：`src/components/LayoutContentEdit.vue`（`submitSave`/`doDelete` 成功段、`onClickSave`/`doDelete` 之 `.finally`）。

## ADR-021: 統計頁查詢失敗用 `getDataError` 通用訊息（非 `$transErr` 反查 err-key）

- **背景**：統計資訊頁 `getStaEvent` 失敗時須顯示錯誤訊息。
- **決策**：`LayoutContentStats.vue` `load`（`:343`）之 catch 設 `errMsg = vo.$t('getDataError')` 通用訊息，**未走 `$transErr(err)` 反查 err-key**（與編輯頁 `submitSave`/`doDelete` 之 catch 走 `$transErr` 不同）。
- **取捨**：`getStaEvent` 後端為 `staEvent` 讀 log 資料夾統計，其失敗未必對應 procLang 有對照之 err-key（可能為檔案 I/O / 解析等動態例外），若硬走 `$transErr` 查無 key 反而 fallback 成 `anUnexpectedErrorOccurred`。故統計頁採安全通用 fallback `getDataError`（語意為「取資料失敗」，已於 procLang 備 eng/cht），不嘗試對非 err-key 之失敗做反查；此為查詢類失敗之取捨。
- **落地**：`src/components/LayoutContentStats.vue`（`load` 之 catch）、`server/staLogs/staEvent.mjs`（後端統計）。

## ADR-022: 套件授權責任 — `verifyConn` 僅做 token 認證，授權由套件使用者 wiring 決定

- **背景**：審計初期曾將「`verifyConn` 連線層只驗 token、未驗 `isAdmin==='y'`」列為套件資安問題。經釐清：此屬「套件使用者如何 wiring 授權」之責任，**非套件本體 `WWebApi.mjs` 之缺陷**——開發者引用套件後之配置（demo `srv.mjs` 之寬鬆設定）不能反算為套件 bug。
- **決策**：套件之 `verifyConn`（內建連線閘）僅負責**認證**：呼叫使用者提供之 `getUserByToken` 解析 token→user，再經 `checkUser` 驗欄位齊備。**授權**（限管理員等）不由套件在連線層強加，保持 unopinionated。
- **使用者授權鉤子**：①**`getUserByToken` 對非授權者回 `{}`**（最直接，且為 kpFunExt（proxyRequest/saveApi/deleteApi/getStaEvent）唯一可由使用者控制之授權點——kpFunExt 不經 ORM、不受 useCheckUser 約束）；②`verifyClientUser`/`verifyAppUser`（套件已套用於 HTTP 端點 getUserByToken/syncAndReplaceTabs）；③`WServOrm` 之 `useCheckUser`/`useExcludeWhenNotAdmin`（ORM exec 層 select/insert/save/del 之授權）。
- **取捨**：採「認證/授權分離、不對連線層強加政策」之 unopinionated 設計，換取使用者彈性；代價是使用者**須自行確保授權**。demo `srv.mjs` 之 `verifyClientUser = isAdmin==='y'` 僅示範 HTTP 端點授權，**連線層 kpFunExt 之授權須使用者於 `getUserByToken` 自行把關**（如對非管理員回 `{}`）。若未來需「套件層連線授權選項」，可加向後相容 opt（如 `verifyConnAuthz`）由使用者啟用，本版先以文件界定責任。
- **落地**：`server/WWebApi.mjs`（`verifyConn`→`p.checkToken`、`getAndVerifyClientUser`、`checkUser`）；使用者於 `srv.mjs` 提供之 `getUserByToken`/`verifyClientUser`/`verifyAppUser`。

## ADR-023: 統計 unit 測試置於 `server/staLogs/`、採 `test_` 前綴與 node assert（非 mocha）

- **背景**：專案測試檔命名慣例為 `test/unit-*.test.mjs`、`test/api-*.test.mjs`、`test/e2e-*.test.mjs`（皆 mocha `describe`/`it`）。唯 `server/staLogs/test_staEvent.mjs` 為 `test_` 前綴、置於**被測模組同目錄**、以 `node assert` + `main().catch` + `process.exit` 撰寫。
- **決策**：維持此例外，不搬入 `test/`、不改寫為 mocha。
- **理由**：①mocha 預設 spec glob 為 `./test/*.{js,cjs,mjs}`（專案無 `.mocharc`、`package.json` 亦無 mocha 區塊），此檔若置於 `test/` 會被自動掃入，其 top-level `main()` 在 mocha 收集階段執行將造成非預期行為；②與被測模組 `staEvent.mjs` 同置便於對照；③由 `package.json` 之 `"test": "node server/staLogs/test_staEvent.mjs && mocha ..."` 於 mocha 之前顯式執行，不會漏跑。
- **取捨**：換取「零 mocha 掃描干擾 + 模組同置」，代價是測試檔命名/位置不完全一致。屬**組織性不一致，非功能缺陷**。
- **補記（2026-09-12）**：全域 §16.5 起 `package.json` scripts 僅留 `test`（單一 mocha 指令），原「`node server/staLogs/test_staEvent.mjs && mocha …`」之顯式前置執行不復存在，該 standalone 檔將永遠不被跑到。已改寫為 mocha 格式之 `test/unit-staEvent.test.mjs`（describe/it，臨時 log 落 `test/_tmp/_logs-unit-staEvent`，失敗路徑亦於 `after` 清理），原檔移除；本 ADR 之①②③理由隨之作廢，僅留作歷史。
- **落地**：（2026-09-12 起）`test/unit-staEvent.test.mjs`，由 `npm test`（單一 mocha 指令，全域 §16.5）納入；原 `server/staLogs/test_staEvent.mjs` 與 `test:unit` script 已移除。

## ADR-024: `e2e-setup.mjs` 之 root teardown 註冊靠「被測試檔 import」而非 mocha glob 載入

- **背景**：`e2e-setup.mjs` 非測試檔，其 top-level 之 `globalThis.after(cleanup)` 是 e2e lifecycle 對稱性所需的 root teardown 註冊點。原置於 `test/` 而被 mocha 預設 glob（`./test/*.mjs`）載入；2026-09-12 依全域 §16.4 搬至 `test/tools/`，`npm test` 之 glob `test/*.test.mjs` 不再直接載入它。

- **取捨**：唯一約束不變——該檔 top-level 只做 export 與 hook 註冊，不得有 top-level `throw`（會於收集階段炸開）。

## ADR-025: `procProxy` / `procLang` 不另建 unit 測試，由 e2e 整合覆蓋主路徑

## ADR-027: 統計頁事件切換由 echarts 圖例提供，移除自建 checkbox；E2E-002 一併移除

- **背景**：統計資訊頁原於控制區自建一組事件 checkbox（chip）供勾選要顯示之事件，但圖表本身之 echarts 圖例（legend）已內建「點擊切換該系列顯示/隱藏」，兩者為重複功能，且並存時使用者會困惑於「兩處狀態是否同步」。
- **決策**：移除自建 checkbox 區（含全選/清除按鈕、計數），事件之顯示/隱藏一律由 echarts legend 提供；`seriesKeys` 改為直接等於 `allEvents`（資料中所有事件皆成系列）。原 **E2E-002（選取部分事件，圖表只顯示所選）一併移除**，E2E-003 / E2E-004 維持原編號不重編（避免變動既有 baseline 檔名）。
- **E2E-002 移除之理由（非因難測而迴避，係標的已不屬本專案行為）**：
  1. **標的變成第三方套件功能**：legend 之 toggle 由 echarts 實作，本專案不再有對應程式碼；測它等於測套件本身。
  2. **無可靠 user-facing 斷言途徑**：legend 繪於 canvas 內、無 DOM 節點——act 只能降級為絕對座標點擊（技能 selector 優先序第 ④ 級），assert 則因圖表區採「貼圖覆蓋凍結」而無法由 pixel baseline 觀察，僅剩讀 echarts 內部 state（L5 evaluate），違反「assert 須走 user-facing observation」。
  3. 保留一個 act/assert 皆須降級的 case，只會產生看似有覆蓋、實則驗不到東西的假測試。
- **仍受保護之部分**：「各事件各成一系列、各自顏色可區分」此一本專案行為，改由 E2E-001 以**統計表逐事件成列**（DOM 可觀察；表列與圖表系列同源於 `allEvents`）+ 圖表 canvas 存在 + pixel baseline 共同守住。
- **行為差異（已知並接受）**：舊 checkbox 取消某事件時該系列**不被建立**，長條寬度會依剩餘系列數重算；legend 取消則系列仍存在僅隱藏，長條寬度不變、原位留空。視覺聚焦效果一致，故接受。
- **連帶清理**：i18n 鍵 `selectEvents` / `selectAll` / `selectNone` 成為孤兒已移除；`.evt-grid`/`.evt-chip`/`.evt-name`/`.evt-sel-btn`/`.evt-count` 等 CSS 一併移除（`.evt-dot` 統計表仍用故保留）。
- **落地**：`src/components/LayoutContentStats.vue`、`test/e2e-stainfor.test.mjs`、`spec/流程_統計資訊.md`、`server/procLang.mjs`。

## ADR-029: 測試分頁請求內容原文送出；後端 HTTP 呼叫改用 Node 內建 fetch (2026-09-07)

**Status**: Accepted (2026-09-07)

**Context**:
- 測試分頁 `submitSend` 於 `contentType` 含 json 時以 wsemi `j2o(rawBody)` 解析 body，而 `j2o` 對非法 JSON 與空字串皆回 `{}`，故使用者打壞的 JSON 或清空的 body 會被**靜默換成 `{}` 送出**且無提示；`: rawBody` 後備分支對非法 JSON 不可達。對 API 測試工具而言，代換 payload 等於工具說謊（打錯逗號會看到「缺欄位」而非「JSON 格式錯」、無法測目標對壞 JSON 的處理）。
- 對標（本套件 UI 參考 Scalar；另對 Postman）：兩者皆「打什麼送什麼」——Scalar api-client 以 `new TextEncoder().encode(text)` 原封送位元組、空文字不帶 body（`har-to-fetch-request.ts` / `build-request-body.ts`）；Postman raw 模式編輯器只給語法提示不擋、照送由目標拒絕。
- axios 1.18 之預設 `transformRequest` 對「JSON content-type + 非 JSON 字串」會 `JSON.stringify` 成字串字面值（實測 server 收到 `"{\"a\":1,}"`），無法原文送出；且對 POST 無 Content-Type 時自動補 `x-www-form-urlencoded`。Node 內建 fetch 無此轉換層：字串 body 原封（但會補 `text/plain`）、`Uint8Array` body 原封且不補任何標頭——與 Scalar 作法一致。
- 專案直接使用 axios 之處僅三：`procProxy.mjs`、`provideTabs.mjs`、`srv.mjs`（皆 Node 端）；前端無直接 axios（僅自有套件 `w-converhp` client 內部使用，由套件端另行處理，不在本 ADR 範圍）。Node v24 內建 fetch / `AbortSignal.timeout` / `Headers.getSetCookie` 皆可用。

**Decision**:
- **前端**：`submitSend` 不再解析 body；非 GET/HEAD 且 body 非空即以原字串交 proxy，空白不帶。Content-Type 由標頭表之列決定（seedFromItem 仍依 `item.contentType` 預帶一列）。
- **後端 `procProxy.mjs` 改用 fetch**：字串 body 以 `TextEncoder` 轉位元組原封送出、不補 Content-Type；物件／陣列 body（其他呼叫端）JSON 序列化、無 Content-Type 才補 `application/json`；GET/HEAD 不帶 body；query 以 `URL.searchParams.append` 併入（保留既有 query）；標頭僅剝除 host / content-length 與 hop-by-hop（connection / keep-alive / transfer-encoding / te / trailer / upgrade / proxy-connection；Node fetch 對其中數個直接拋錯，且 RFC 7230 §6.1 本就不得轉送），其餘原樣；4xx/5xx 視為有回應；`AbortSignal.timeout`；回應 text 可 `JSON.parse` 者回物件否則原文（對齊改造前 axios 之 silent JSON parsing，`dataToText` 顯示形式不變）；`set-cookie` 多值以陣列呈現；例外 `srLog.error({ event:'proxyRequest-fetch', msg, cause })` 後 reject `errProxyRequestFailed`（err-key 不變）。
- `provideTabs.mjs` / `srv.mjs` 之 axios 呼叫改 fetch；非 2xx 以 `res.ok` 判定維持原語意（provideTabs 之 reject 仍為 Error 物件、訊息同 axios 格式）。`package.json` 移除直接依賴 `axios`（`w-converhp` 之傳遞依賴不受影響）。
- **刻意差異**：企業 proxy 環境變數（`HTTP_PROXY` 等）axios 預設支援、fetch 須以 `NODE_USE_ENV_PROXY=1`（Node 24 旗標）開啟——部署於企業 proxy 後時須設定，記於此。`Expect` 等 fetch 不支援之標頭不剝除、由 fetch 拋錯映射為 `errProxyRequestFailed` 並 log cause（罕見、不預先代使用者決定）。

**驗證** (2026-09-07)：
- `test/unit-procProxy.test.mjs`（起真 http server 直打 `proxyRequest`，不 mock）：非法 JSON 原封／空 body 不帶／字串 body 不補 Content-Type／物件 body 補 json 且不覆蓋既有／回應形狀（parse、原文、4xx、204、set-cookie、durationMs）／逾時與連線拒絕 reject + log／url 檢核與 isAllowTarget／query 併入與標頭剝除／GET/HEAD 不帶 body，10 case。
- e2e `流程_測試API.md` 新增 E2E-010（非法 JSON 原文送達 echo）、E2E-011（清空不帶 body）；E2E-001~009 回歸；改造前 E2E-008 之 echo 斷言與 baseline 不受影響（合法 JSON 原文與 stringify 後 wire 等價）。
- **標準圖重產（僅 2 張，經授權）**：`apitest-{eng,cht}-E2E-001-3-response.png`。原因非缺陷——**axios 解壓 gzip 後會刪除回應之 `content-encoding` 標頭，fetch 保留**（起後端實測比對標頭集合，兩者唯一差異即此鍵），故回應標頭面板多一行、其遮罩區高 283→304px（一行）、卡片捲動位置上移 22px 而 baseline 判 fail；body 文字裁圖逐行相同。顯示 `content-encoding` 更貼近目標真實回應（Postman / devtools 亦顯示），故重產 baseline 而非改實作。同 case 之第 1、2 張（seeded / url-changed）未受影響，產製後以 `git checkout --` 還原並比對 md5 確認未變動。

**Affected**：
- server/procProxy.mjs（重寫）；server/provideTabs.mjs；srv.mjs；package.json
- src/components/LayoutContentTest.vue（submitSend）

## ADR-030: 全面盤查後之 8 項必修 (2026-09-07)

**Status**: Accepted (2026-09-07)

**Context**:
以 6 個維度（後端端點契約 / i18n 與 UI 契約 / 資安穩健 / 路徑與資源生命週期 / 測試覆蓋 / 契約缺陷與對稱破缺）盤查全套件，收回 40 項原始發現，逐條對源碼核實後採納 32 項、駁回 1 項、降級 3 項，其中 8 項列為必修。複審另補查 XSS 軸（原六維度未涵蓋）：三個 `v-html` sink 皆安全（`w-md2html` 實測會剝 `onerror` / `javascript:` / `<script>`；兩處 JSON 高亮皆先 escape `< > &`），不需處置。

**Decision**（逐項修法與取捨）：

1. **`getStaEvent` 之 `timeLength` 輸入閘（DoS）**：`genPlan` 於 `subtract` 前驗證 `Number.isInteger && 0 ≤ v ≤ MAX_TIME_LENGTH_DAY(3650)`，否則 throw `errTimeLengthInvalid`；`staLogs` 攔截該同步 throw 轉為 **reject 字串 err-key**（`wrapErrLog` 記到的才是 key、前端 `$transErr` 才查得到文字）。**根因**：dayjs 對非數字／NaN／超 Date 範圍之值回 Invalid Date，其 `isAfter` 恆 false，使 `while (!tCurr.isAfter(tEnd))` 成為**主執行緒同步無窮迴圈**（位於 `staLogs` 第一行，早於 worker 派工），單一 RPC 呼叫即凍結整個伺服器且 try/catch 無效。實測 `'abc'`／`1e9` 皆 8 秒不返回。**可達範圍**：`checkUser` 僅要求 `isAdmin ∈ {y,n}`，故 demo 接線下**非管理員亦可觸發**。上限取 3650 之理由：hr 粒度下 kpTime 約 87600 筆仍可接受，再大則僅建陣列即長時間阻塞。
2. **`DEL` → `DELETE`**：新增 `mShare.methodToHttpVerb`，於送出（`submitSend`）與 cURL 產生（`curlOf`）兩處共用。**根因**：`DEL` 非 HTTP 動詞，實測以 fetch 送出時目標於 HTTP 層直接回 400、handler 完全不執行，種子資料 3 支 `method:'del'` 之 API 全數無法測試。**刻意不改**資料層與顯示層之 `del`／`DEL`（屬既有資料模型與視覺慣例），只在「轉成 wire 動詞」處映射。
3. **憑證遮罩對稱化**：`getAndVerifyAppUser` 之 `console.log('token', token)` 補 `maskTok`；新增 `maskQuery` 用於三處 `console.log('req.query', …)`。**根因**：原三處「先印整包 query、下一行才印遮罩後 token」，等同把自訂之遮罩政策在上一行繞過；其中 `keyTable` 無效分支之 token 為**已通過檢查的真實有效憑證**。
4. **`logNumKeep` 接線**：`srv.mjs` 補傳 `logNumKeep`。**根因**：`settings.json` 宣告、JSDoc 記載、`srLog` 讀取與驗證、單元測試直呼 `srLogInit` 皆存在，唯獨 demo 入口未從 stApp 讀出轉傳，使該設定**靜默無效**、且「給錯值即 throw」之 fail-fast 永不觸發。修後實測：`logNumKeep:'abc'` 啟動即 throw、不進入監聽。
5. **樹根標籤 i18n**：`convertToTree` 之 `bindRoot` 由中文字面值 `'全部'` 改為哨符 `KEY_TREE_ROOT`，顯示文字於 template 經 `treeRowText()` 取 `$t('treeRootAll')`。**取捨**：不在 `genTree` 時把譯文烤進樹資料——語系為**就地切換**（`setLang` + forceUpdate 廣播，不重載頁面），烤進去會停在舊語系直到樹重建。附帶修正原字面值會與同名 group 資料相撞。
6. **認證失敗入 srLog**：新增 `wrapRouteErrLog`（與 kpFunExt 之 `wrapErrLog` 同構）包住兩支 HTTP route 之 `core`；`verifyConn` 之 token 空分支補 `srLog.error`、`checkToken` 以 try/catch 攔截記錄後原樣再拋。**取捨**：於**邊界**收斂而非逐個 reject 點加 log，避免同一規則散落多處。**根因**：統計頁與稽核讀的正是 srLog，原錯誤路徑僅 `console.log`，導致認證失敗永不可見。修後實測三種失敗皆產生 `ERROR` 記錄並帶 err-key。
7. **e2e 走完 spec 操作鏈**：`e2e-edit` 新增 `clickModalOk`；E2E-001 **先點 OK 再截圖**（spec 該步視覺為「改名後 docs 標頭」，彈窗須先關閉），E2E-002 **截圖後才點 OK**（spec 該步視覺即為「儲存成功 modal」）。**根因**：spec 操作鏈以「成功 modal 點 OK」結尾而測試等到彈窗出現即止，`CheckYes` 之 OK 鈕在全套 case 中零覆蓋。
8. `dist/` 依 `script.txt` 發版尾段（build → genEntry → gDistRollup）重建；屬例行產製，非缺陷。

**刻意不做**（本次盤查列為待討論、未處置者，見盤查紀錄）：`redirect:'follow'` 繞過將來之 `isAllowTarget`（ADR-006 接線時須一併處理）、`isearr([null,null])` 通過驗證後洩漏原始 TypeError 訊息、Query/Headers 重複鍵被收斂、Content-Type 雙列靜默覆蓋、kv 表 `:key=idx` 刪列錯位、新增模式欄位非響應式、測試分頁無頁面層 loading、`$alert` toast 與 modal 政策衝突、`getApisList` 繞過 procOrm、統計頁原生 `<select>`、連線狀態文字兩份手寫、`provideTabs` 白名單與 schema 漂移、method 清單三處手寫、`state.userSelf` 非響應式、兩套 JSON 高亮行為不對稱（Test 分頁鍵值不上色）。

**驗證** (2026-09-07)：
- L0a 6 檔語法與 import 通過；L0b eslint 新增 0（3 個既有錯誤與 HEAD 版逐一相同）。

## ADR-031: ADR-030「刻意不做」清單之逐項處置 (2026-09-13)

**Status**: Accepted (2026-09-13)

**Context**：
ADR-030 收尾時把 16 項列為「待討論、未處置」。使用者指示「還有什麼確定的問題還沒修 就去修」，逐項對源碼與實測核實後分三類：**契約缺陷**（guard 有洞／affordance 未兌現／同型不對稱，全域 §8 第四類，修）、**收斂**（同一規則手寫多處，修）、**設計取捨**（不修、留紀錄）。本 ADR 為該清單之處置紀錄；各項之契約文字已寫入對應流程文件（`流程_測試API.md`「規則摘要」、`流程_統計資訊.md`、`流程_編輯API.md`）。

**Decision**（逐項修法與取捨）：

1. **`syncAndReplaceTabs` 逐列檢核**（契約缺陷）：陣列層改 `isarr && length>0`（wsemi `isearr` 僅長度 1 時檢查元素，`[null]` 與 `[null,null]` 原本分岔），逐列檢核分兩段——①每列須為物件；②b64 還原後必填欄位（`kpRequiredFields.apis = ['name','url']`，與編輯表單同步檢測對稱）須為非空字串——任一列無效即整批 `reject('errRowInvalid')`（新 key，eng/cht），且**一律在 `delAll` 之前**（既有群組資料不動）；列索引與欄位名 `srLog.error({ event:'syncAndReplaceTabs', err, keyTable, group, index, field })`，回呼叫端只給 key（同其他錯誤契約）。**根因**：`[null,null]` 通過 `isearr` 後 `v.group=` 即 TypeError、原始例外訊息經 `pm2resolve` 外洩；`[{}]` 經 `ltdtmapping` 補空值後以空名稱進樹。`id`／`timeCreate` 不列必填：LMDB insert 缺 id 自配 `genIDSeq`、procOrm 補 `timeCreate`（實測）。
2. **轉址逐跳檢核 `isAllowTarget`**（契約缺陷：guard 有洞）：`procProxy` 改 `redirect:'manual'` 手動跟隨（上限 20 跳，同瀏覽器／undici），每一跳重驗 `isAllowTarget`；方法／body 改寫依 Fetch 標準 §4.4（301/302 之 POST 與 303 改 GET、丟 body 與 content-* 標頭；307/308 保留）；跨來源剝除 Authorization；3xx 無 Location 視為最終回應；整條鏈共用一個 `AbortSignal.timeout`；轉址鏈之拒絕 `srLog.error({ event:'proxyRequest-redirect', err, msg })`。**附帶補接線**：建構子 `opt.isAllowTarget` 原本從未傳入 `procProxy`（hook 存在但套件使用者無從設定＝有 prop 無效），現接線並補 JSDoc。undici 之 `redirect:'manual'` 回**真實** 3xx 回應（非瀏覽器之 opaque-redirect），PROXY-012 實測確認。
3. **Query／Headers 重複鍵不收斂**（契約缺陷）：前端以 `mShare.kvRowsToPairs` 產有序鍵值對 `[[key,value],…]` 送出（僅 on 且鍵非空之列）；`procProxy` 之 `toPairs` 同時接受物件（向後相容；值為陣列＝同鍵多值）與鍵值對，query 逐對 `searchParams.append`，標頭改建 `Headers` 逐對 `append`——重複鍵由平台依 Fetch 標準合併（`, `；cookie `; `，undici 實測），不自寫合併規則。**根因**：改造前 `obj[key]=value` 收斂，同鍵後列靜默覆蓋前列。
4. **Content-Type 雙列**（契約缺陷）：`seedFromItem` 於預設標頭已明給 Content-Type（不分大小寫）時不再補 `contentType` 列（對標 Postman：明給之標頭優先於自動標頭）。第 3 項改鍵值對後此項成為**必要**——否則兩列會被合併成 `a, b`。
5. **kv 表 `:key=idx`**（收斂＋正確性）：列建立點收斂為 `mkRow()`（改造前 10 處手寫 `{ on, key, value }`），列帶單調遞增 `id` 作 `:key`。未重現使用者可見錯位（Vue 以 v-model 重同步 DOM），列為收斂順帶修正；`.kv-del-btn` 原為建構器唯一零覆蓋之可點元素，E2E-007 補刪列步驟。
6. **兩套 JSON 高亮**（收斂＋缺陷）：`mShare.jsonHighlight`（單趟 tokenizer：字串 token 優先、字串內之數字／關鍵字不再比對；先 `escapeHtml`）供 docs 與測試分頁共用；測試分頁僅對 JSON 容器回應上色，其餘（HTML／純文字）只 escape（spec 表「字串 → 原文」）。**根因**：測試分頁規則以 `&quot;` 比對但 escape 未換 `"`，鍵值永遠不上色；docs 版逐規則 replace，字串內之數字／true 被誤上色。種子資料下 docs 輸出逐 byte 相同（display 標準圖不需重產）。
7. **統計頁原生 `<select>`**（全域 §10.6-3）：改 `WTextSelect`，色票沿用本頁 token 實值（WShellEllipse 之 `convertColor` 不認 `var()`，實測 `getHexColor` 對未知字串原樣回傳但 `white`／`transparent` 等會被攔，故一律給 hex）；展開圖標隨開闔旋轉；寬度改 computed `timeGroupSelWidth`＝當前語系最長選項文字實寬（canvas measureText、字型取自元件）＋結構 38px，重現原生「依最長選項定寬」（改前後量測表見 `流程_統計資訊.md`：結構寬度 38.3／38.2 → 38.8／38.9、標籤間距 8 不變；寬 +3／+1、高 +1 皆為字型承襲差異——原生控件用 Arial、自製承襲頁面字型，與 `.ctrl-label` 之 19px 列高一致）。E2E-004 改真滑鼠點觸發區→點項目；stainfor 六張與 init E2E-003 標準圖及其 `_staref` 重產。**清單對齊**（§10.6-6）：驗收實測首版項目文字左緣較觸發區文字右偏 8px（WPopup 錨在觸發區之內容元素＝外框＋邊框 1＋內距 8），以 `placementDistX=-9`、清單寬固定＝觸發區寬（關 autoFit、min/maxWidth）、項目左內距 9 校正，複測 eng 191／191、cht 173／173 貼齊；hover 整列填 `--bg-3`、無左緣 bar。
8. **測試分頁頁面層 loading**：`submitSend` 開 `updateLoading(true)`、`finally` 統一關（三層雙擊防護之頁面層；送出對目標可能有副作用）。
9. **`$alert` → `showCheckYes`**（三處：編輯存／刪、測試送出之非預期例外）：先 `updateLoading(false)` 再 `showCheckYes(…, { type:'error' })`（CLAUDE.md 失敗通知政策、ADR-005 modal 政策）。`$alert` 定義保留（三專案共通 prototype、vue-ui 技能範本用字）。
10. **`state.userSelf`**：store 初始 state 宣告 `userSelf: {}`（Vue 2 響應性；同 sso）。
11. **`getApisList` 經 `procOrm`**：`procOrm(userId,'apis','select',{})`——`useCheckUser`／`useExcludeWhenNotAdmin`（非管理員濾 `isActive='n'`）等 ORM 層政策才套到讀取（建構子 JSDoc 明載 select 會過濾，原直呼 `woItems` 使該承諾對本讀取無效）。
12. **方法清單三處手寫**（收斂）：`mShare.METHODS = ['get','post','put','del']` 供編輯表單與測試分頁共用（`kpColorMethod` 為顯示色表，不是清單）。
13. **新增模式欄位非響應式**：`blankApi` 以 `dtmapping(預設值, ds.apis.keys, '')` 補齊 schema 全部欄位——編輯表單以 `cloneDeep(item)` 為 `form`，Vue 2 不追蹤初始不存在之屬性，原本 12 個欄位（tokens／testBaseUrl／authConfigJson／default*Json／md*／*Example／order／id）於新增模式為非響應式。

**不修（留紀錄，屬設計取捨或待使用者拍板）**：
- **連線狀態文字兩份手寫**：`App.vue` 以 `connState` 判可否顯示主畫面、`LayoutState.vue` 以四態 template 顯示文字，狀態鍵由 w-converhp 定義、兩處職責不同，非同一規則手寫兩份；三專案共通結構，不動。
- **`provideTabs` 白名單（設計事實，非缺口）**：外部同步只推送 API 描述資料（`ks_apis`：id／order／name／description／url／method／version／group／levels／keywords／state／creator／dataSource／md*／*Example）。認證不同步——每個服務各自獨立，認證靠自身 token 或 SSO 與 perm，`tokens`／`authType`／`authConfigJson` 由本站編輯表單管理；測試分頁之設定欄位（`testBaseUrl`／`default*Json`／`contentType`）同樣屬本站本地設定，時間欄位由 ORM 補。同步列這些欄位為 `''`：測試分頁對 `authType ''` 視同 none、`contentType ''` 不補列。原列為「待使用者拍板」係誤判（2026-09-13 更正）。
- ADR-016 `delAll→insert` 非原子：維持（本次逐列檢核已把「可預期之失敗」全部移到 `delAll` 之前，殘餘風險僅 insert 本身失敗）。
